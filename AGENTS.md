# Development policy

This project has no actual users yet. Until the maintainer explicitly announces adoption:

- Prefer the current design over backward compatibility. Do not add database migrations, old-format readers, legacy API adapters or fallback execution paths solely to preserve previous project behavior.
- Remove obsolete code and tests with the contract they covered. Keep and adapt tests for current behavior, resource permissions, concurrency, persistence, recovery and atomic publication.
- Accept only explicitly supported current database, project and exchange formats. Reject unsupported formats clearly; never automatically delete existing data files. Standard MIDI interchange support is a product feature, not legacy project compatibility.
- Project undo/redo, recovery and Skill revisions are current product features and must not be removed as compatibility work.
- The current authority is IMPLEMENTATION_PLAN.md, docs/architecture.md and the normative P0 scope contract docs/p0-refactor-contract.md. Read the scope contract before any P0 implementation; summaries do not authorize broader deletion. Archived ICEPick plans and marked old guides are implementation references, not active requirements.

# IceTudio product policy

- IceTudio is an AI native music creation application. The music project and editing workspace are central. MIDI editing and the Agent are native capabilities; conversation is a way to work on the project.
- Users must be able to create, edit, audition and save supported MIDI projects without connecting a model. Agent use must not require learning Profiles, LocalContexts, components, worker slots, workflows or runtime IDs.
- GUI and Agent edits must use the same authoritative project model and command service, with stable object IDs, scoped queries, revision checks, atomic batches and shared undo/redo. Do not make UI automation or file rewriting the primary music editing interface.
- Keep project state and editing history separate from conversation history and model summaries. Deleting a conversation must not delete music. Protect drafts, unsaved projects and edits made while the Agent is thinking.
- Freeze the task's target selection and permission ceiling. Later selection changes do not retarget in-flight work. Reject conflicting edits rather than overwriting subsequent user changes. Do not silently rebase a gesture onto a newer revision.
- Keep MIDI events beyond notes, including supported controller and meta events. Define timing precision, tempo/meter mapping and supported import/export semantics. Validate untrusted inputs before calling libraries with known parser limitations.
- Keep playback scheduling and audio rendering independent of model calls, UI rendering and database work. Explicitly handle stop, seek, loops, sustained notes and edits during playback.
- Preserve MCP, Skills and web search as supported product capabilities. Keep installation/connection, enablement and authorization distinct. Native music editing must not require an external MCP server.
- Preserve per-conversation history, summaries and unfinished task context. Remove the separate persistent cross-conversation memory system; do not silently import other conversations or rebuild hidden user memory through Skills.
- Preserve feedback-driven Skill improvement. Record valuable feedback and explicit improvement requests with scope and evidence. Distinguish a one-off edit from a reusable method. Skill changes must be visible, versioned and reversible; runs use frozen versions/resources. Automatic adoption requires an explicitly enabled scope and cannot expand permissions.
- Delete only the legacy scene templates, Profile management/sharing/generation product contracts and separate long-term memory listed as DELETE in the P0 scope contract. MOVE means retain functionality at a different UI location; REPLACE requires a working equivalent before removing the old carrier; KEEP allows necessary adaptation. Unlisted capabilities default to KEEP.
- Preserve main/planner/worker/reviewer/improver, delegation, direct/dynamic/fixed execution, task graphs, session plans, scheduling, reviews/rework, retrospectives, worker evidence, budgets, cancellation and recovery across services, storage, CLI/IPC and tests. A single user-facing assistant is not a single-agent runtime. Removing configuration UI must not remove execution capabilities.
- Replace the Profile configuration carrier with versioned RuntimeConfig including all role/workflow/worker/budget/capability semantics and provenance. Keep internal authorization contexts. Do not delete Profile storage until replacement paths can actually run and pass the scope contract gates; this refactor is not a legacy-format migration.
- Do not delete mixed files wholesale: app/memory.go also serves summaries/plans; storage/execution.go also registers roles; draft_model, draft_evidence, TaskEvidence and improver support retained Skill improvement. Retain shared symbols and tests or move them with equivalent behavior. Task detail panels and tasks review/retrospect/continue APIs remain available.
- If a proposed deletion is not explicitly covered or conflicts with a KEEP requirement, preserve that capability and document the missing scope decision. Do not infer authorization from unused UI, old filenames, the no-migration policy, or a passing build after deleting tests.
- Present a focused music workspace, transport, context-aware Agent panel and understandable edit previews. Put runtime IDs, raw tool logs, budgets and diagnostics in task details or one Developer settings area.
- Connect provider, model and credentials coherently. Derive sending destinations from the actual endpoint, including custom endpoints. Preserve scope checks, frozen ceilings, live permission restrictions and explicit authorization; never replace them with blanket grants.
- Explain approvals through concrete tracks, regions, files or destinations and consequences. Query committed native operation results after interruptions. For unknown external effects, guide verification and allow remaining unsure; never blindly replay them.
- Use readable Markdown, appropriate scrolling, keyboard/input-method support, clear material handling and native file/folder selection. Normal flows must not require JSON editing, runtime IDs or browser prompt/confirm dialogs. Disabled actions must explain a usable next step.
- Keep the AGPL-3.0-only project direction and third-party obligations. Do not bundle unverified GridSound assets or unlicensed soundfonts/samples. Code licensing does not establish rights to input music, samples or private conversation material.
- Distinguish planned work, isolated experiments and shipped features. Validate offline editing, model connection, actual Agent edits, audition, permissions, undo, interruption recovery and project persistence. Browser mocks and passing builds alone do not establish native usability, audio timing or musical quality.
